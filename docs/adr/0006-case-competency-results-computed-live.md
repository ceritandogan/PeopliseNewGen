# Competency results are computed live from Scorings, not read from the AssessmentResult snapshot

`Case.Complete()` builds an `AssessmentResult` (`CaseResult`/`CompetencyResult`) exactly once, at the moment a case's last step finishes, from whatever `CaseScoring` rows exist at that instant. `GetCandidateComparisonQuery` and `Case.GenerateReport()` both used to read `AssessmentResult.CompetencyResults` directly — but reviewer scoring is normally *post-hoc*: a candidate finishes their video, the case auto-completes with zero scorings yet, and a human reviewer scores it afterward via `SubmitReviewerScoringCommand`, which never touched `AssessmentResult`. In that (the ordinary) sequence, comparison and reports would show a case as unscored forever, even after real scores existed — directly contradicting ADR 0005's own stated goal for the report endpoint ("a reviewer should never see a known-wrong report"), which turned out not to hold because the field it reads from was itself the stale part.

Both read paths now call a new `Case.GetCurrentCompetencyResults()`, which recomputes fresh from `Scorings` (the same per-competency weighted average `CalculateCompetencyResult` already does, reused rather than duplicated) on every call — the same "recompute on read" philosophy ADR 0005 already established, just applied one level deeper than where it originally stopped. We considered instead refreshing the persisted `AssessmentResult` from `SubmitReviewerScoringCommand` whenever it scores an already-completed case — rejected because it means two separate write paths (`Complete()`, `SubmitScoring`) both have to remember to keep the snapshot current, for no benefit over computing it fresh each time reads are already cheap and deterministic.

`Complete()` still builds and persists `AssessmentResult` exactly as before — nothing reads it anymore, but it stays as a write-only historical snapshot of "what was known at completion time." We considered removing `CaseResult`/`CompetencyResult` entirely — rejected because `AnonymizeMediaAndIdentity`'s own remarks (Stage 10/12, KVKK) describe scorings/results as deliberately preserved post-anonymization for aggregate statistics; discarding that persisted snapshot in a bug-fix change would cut against an earlier, deliberate decision it wasn't this change's place to revisit.

## Consequences

- `AssessmentResult`/`CaseResult`/`CompetencyResult` are now write-only from the read paths' perspective — same accepted trade-off ADR 0005 already made for `Report`/`ReportSectionContent`. A future reader who sees `Complete()` building a `CaseResult` and assumes it's what comparison/report display will be wrong; both now point at `GetCurrentCompetencyResults()`.
- Comparison and reports recompute `Scorings` on every read rather than reading one persisted column — cheap today (no AI call, small per-case scoring counts), same reasoning ADR 0005 already accepted.
- If `CaseResult`'s snapshot value is ever actually needed (e.g. real aggregate-statistics reporting), it is still there, still accurate as of `ComputedAt` — this change only stops two specific read paths from trusting it as current.
